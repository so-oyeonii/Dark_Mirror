# 실제 서비스 연동 전 체크리스트

작성일: 2026-10-29

키 없이 실행되는 로컬 기능과 실제 인증·DB·LLM·공유 서비스는 구분한다. 이 문서는 실제 연동을 위한 준비 및 검증 항목이다. 체크되지 않은 항목을 구현 또는 검증 완료로 해석하지 않는다. 환경변수에 키가 입력되었다는 이유만으로 실제 서비스를 자동 활성화하지 않는다.

## 현재 DB 준비물과 검증 한계

- `0001_initial.sql`은 원본 그대로 보존한다. `0002_ownership_and_lifecycle.sql`에 개인 데이터의 소유권 RLS, 달력 입력 제약, 궁합 카드의 부모 연결과 철회 시각 필드를 추가한다.
- `profiles`는 인증된 소유자의 CRUD를 허용한다. `birth_profiles`는 본인 조회·삭제와 원본 입력 컬럼의 생성·수정만 허용한다. `saju_json`, `engine_version`, `converted_solar_date`의 클라이언트 INSERT/UPDATE 권한은 없으며 서버만 기록한다.
- 출생 원본의 날짜·시간·달력·윤달·시간대가 바뀌면 DB 트리거가 기존 사주 결과·엔진 버전·양력 변환값을 자동으로 NULL 처리한다. 서버는 원본을 저장한 다음 별도 문장에서 검증한 결과를 기록해야 한다.
- `test_attempts`는 본인 조회·삭제와 `in_progress`·완료 시각 없음 조건의 초안 생성만 허용하고, 상태 UPDATE는 서버 전용이다.
- `test_answers`는 소유자 조회를 허용하고, 생성·수정·개별 삭제는 부모 검사가 `in_progress`일 때만 허용한다. 부모 행을 잠그는 트리거가 답안 변경과 서버 완료 처리를 직렬화하며 완료 후 답안 변경을 막는다. 완료 검사 전체를 삭제하는 FK cascade는 허용한다.
- `test_scores`, `simulation_sessions`, `simulation_messages`는 인증된 소유자의 조회·삭제만 허용한다. 생성·수정은 검증된 서버가 담당한다. 답안·점수·메시지는 부모 검사·세션의 소유권까지 확인한다.
- 플랫폼의 기본 테이블 권한도 회수한 뒤 필요한 권한만 부여한다. RLS가 적용되지 않는 `TRUNCATE` 권한을 클라이언트에 남겨두지 않는다.
- `compatibility_pairs`, `compatibility_consents`, `compatibility_reports`, `share_cards`는 `anon`, `authenticated`, `PUBLIC`의 테이블 권한을 회수한다. 별도의 restrictive deny RLS도 적용하며, 참여자라도 직접 SELECT할 수 없다. 초대·공개 토큰 해시는 브라우저 조회 대상이 아니다.
- 테스트는 PGlite의 로컬 PostgreSQL에서 실제 마이그레이션과 RLS를 실행한다. 테스트용 `auth.users`, `auth.uid()`와 요청 사용자 ID 설정은 Supabase 인증을 대신하는 fixture이며 JWT 발급·검증이나 운영 Supabase를 검증하지 않는다.
- 테스트 환경에서 사용할 수 없는 `create extension if not exists pgcrypto;` 행만 생략한다. 테이블·제약·RLS 문장은 그대로 적용하며 UUID 생성은 PostgreSQL 코어 기능을 사용한다.
- 역할 변경은 `SET ROLE anon/authenticated`로 수행한다. 테이블 소유자·관리자로 조회한 결과만 보고 RLS가 작동한다고 판정하지 않는다.
- 기존 초기 스키마가 아직 배포되지 않았다는 전제다. 실제 데이터가 이미 있다면 새 제약 적용 전 데이터 마이그레이션을 설계하고 검증해야 한다.
- 로컬 정책 테스트 통과는 운영 Supabase·PostgREST·Storage·이메일 인증의 검증 완료가 아니다. 실제 실행 결과는 테스트 보고에서 별도로 기록한다.

## 인증·계정 연결

- [ ] 사용자 소유 Supabase 프로젝트와 서비스 계정을 준비하고, 개발·운영 환경 및 허용 리디렉션 URL을 구분한다.
- [ ] 이메일 매직 링크 발송·콜백·세션 갱신·로그아웃·만료·오류 흐름을 실제 환경에서 확인한다.
- [ ] 서버는 신뢰할 수 있는 인증 결과로 사용자 ID를 결정한다. 요청 body/query의 `userId`를 권한 근거로 삼지 않는다.
- [ ] 쿠키·리디렉션·오픈 리디렉션 방지와 로그인 요청 제한을 검증한다.
- [ ] 게스트 기록 이전은 명시적인 동의를 받은 뒤 검증된 입력만 처리한다. 중복 요청·부분 실패·동일 기록 재이전의 결과를 정한다.
- [ ] 로그에는 토큰, 원문 답안·대화, 출생정보, 이메일 인증 링크를 남기지 않는다.
- [ ] 서비스 역할 키는 서버 전용으로 보관한다. 서비스 역할은 RLS를 우회할 수 있으므로 서버 소유권·참여자·동의 검사를 별도로 수행한다.

## 운영 DB·RLS A/B/익명 검증

- [ ] 실제 Supabase 프로젝트에 마이그레이션을 적용하고 모든 대상 테이블의 RLS 활성화를 확인한다.
- [ ] 실제 로그인한 사용자 A/B와 익명 요청으로 개인 데이터 조회·추가·변경·삭제를 확인한다. A가 B의 행을 읽거나 부모 FK를 바꿔 B에게 행을 이동시킬 수 없어야 한다.
- [ ] 답안·점수·메시지의 부모 체인을 따라 소유권이 검사되는지 확인한다.
- [ ] 클라이언트의 완료 상태·점수·AI 역할·턴 수 조작을 거부하고, 완료 후 원본 답안 추가·수정·개별 삭제가 차단되는지 확인한다.
- [ ] 사주 결과·엔진 버전·양력 변환값에 대한 클라이언트 INSERT/UPDATE가 거부되고, 원본 입력 수정 시 생성값이 자동으로 비워지는지 확인한다.
- [ ] 궁합·동의·보고서·카드 테이블과 토큰 해시가 참여자 및 익명 브라우저에서 직접 조회되지 않는지 확인한다.
- [ ] RLS와 별도로 서버 입력 스키마·상태 전이·쓰기 요청 제한을 검증한다. 소유자가 수정할 수 있는 초안 응답과 프로필도 서버에서 다시 검증한다.
- [ ] 서버 완료 처리는 부모 attempt 행을 잠그고 문항 수·버전·답안을 검증한 뒤 재채점·점수 저장·완료 상태 변경을 하나의 트랜잭션으로 처리한다. 동시 답안 수정·완료·삭제 요청에서 결과가 어긋나지 않는지 실제 연결에서 검증한다.
- [ ] AI 턴 수·역할·완료 상태는 서버가 통제한다. 행 소유권 RLS가 턴 중복·상태 전이까지 보장한다고 가정하지 않는다.
- [ ] 운영 응답·오류 메시지와 모니터링 로그에 비공개 필드가 포함되지 않는지 확인한다.

## 출생정보와 검증 엔진

- [ ] `birth_date`는 원래 양력 날짜에만 사용한다. 음력 원본은 `birth_year`, `birth_month`, `birth_day`, 윤달 여부로 저장하고, 변환 결과는 `converted_solar_date`에 별도로 기록한다.
- [ ] DB의 월·일 범위 제약을 실제 음력 날짜 검증으로 설명하지 않는다. 검증된 음력·윤달·절기·시간대 엔진을 선정하고 경계 사례를 확인한다.
- [ ] 검증 엔진이 없으면 `converted_solar_date`, 사주 계산 결과를 생성하지 않고 준비 중 상태를 유지한다.
- [ ] 입력 달력·원본 날짜·시간·시간대 변경 시 자동 무효화 동작을 확인한다. 검증 엔진은 서버에서 실행하고, 원본 저장 뒤 생성값과 엔진 버전을 기록한다. 계산 중 원본이 변경되지 않았는지 서버 트랜잭션 또는 버전 검증으로 확인한다.

## 상호 동의·철회·토큰 수명

- [ ] 초대 토큰은 충분한 난수로 생성하고 DB에는 해시만 저장한다. 72시간 만료, 일회 사용, 참여자 확인을 원자적으로 처리한다.
- [ ] 공유 필드 허용 목록과 동의 버전을 기록하고 양쪽 동의 전 생성·열람을 거부한다. 원본 생년월일·답안·채팅 내용은 공유하지 않는다.
- [ ] 동의 철회는 해당 동의, pair, 보고서, 연결 카드의 철회 시각·상태를 함께 갱신하는 서버 트랜잭션으로 처리한다.
- [ ] 2인 카드 생성 서버는 `share_cards.pair_id`를 반드시 연결한다. DB에는 관계 FK가 준비되어 있지만 카드 종류별 생성 규칙은 후속 서버에서 검증해야 한다.
- [ ] 공개 토큰 조회는 매번 만료·철회·소유자 존재·양쪽 동의를 확인한 뒤 안전한 필드만 반환한다. 토큰이 개인 결과 원본을 조회하는 수단이 되지 않게 한다.
- [ ] 캐시·생성 이미지·공유 링크를 철회 시 무효화한다. `revoked_at` 컬럼 추가나 DB 행 삭제만으로 이미 발급한 Storage URL이 무효화되지는 않는다.
- [ ] 공유 이미지가 이미 내려받아졌거나 제3자가 복제한 경우 서비스가 그 복사본을 회수할 수 없다는 한계를 안내한다.

## 삭제·Storage 정리

- [ ] Storage 버킷은 기본 비공개로 설정하고 짧은 유효기간의 URL을 필요한 범위에만 발급한다.
- [ ] DB의 기존 FK cascade를 확인한다. `auth.users` 삭제 → 프로필·출생정보·검사·답안·점수·AI 세션·메시지·궁합 관련 행이 연쇄 삭제되어야 한다.
- [ ] 궁합 pair 삭제 시 `share_cards.pair_id ON DELETE CASCADE`로 상대방이 소유한 해당 궁합 카드도 정리되고, 관계없는 상대방 개인 기록은 남아야 한다.
- [ ] DB 삭제 전에 정리할 Storage 경로를 내구성 있는 삭제 작업 목록에 확보한다. FK cascade 이후에는 원래 Storage 경로를 DB에서 얻을 수 없을 수 있다.
- [ ] 공개 노출을 먼저 차단하고 Storage 삭제를 재시도 가능한 작업으로 처리한다. 부분 실패·재시도·중복 삭제·최종 완료 확인을 검증한다.
- [ ] 단일 기록 삭제와 전체 계정 삭제를 각각 확인하며 외부 공유 링크·캐시·생성 파일을 함께 정리한다.
- [ ] 실제 Storage가 아직 연결되지 않았다면 파일 삭제가 검증되었다고 표시하지 않는다.

## LLM·비용·출시 정책

- [ ] 실제 LLM 제공자·모델·서버 환경을 선정하고 출력 JSON 검증, 오류·타임아웃·재시도·멱등성을 검증한다.
- [ ] 사용자 5턴 제한과 중단, 위험 상황에서 역할극 종료, 개인정보 최소화, 비진단 표현을 확인한다.
- [ ] 계정·IP·기능별 요청 제한, 일일 비용 상한, 토큰·응답 길이, 동시 요청 한도를 정한다. 상한 도달 시 안전하게 중단하고 비용이 계속 발생하지 않게 한다.
- [ ] 서비스 대상 연령, 개인정보 수집 항목·보존·삭제 기간, 외부 제공자 처리, 동의 문구·철회 방법을 확정하고 공개 출시 전에 검토한다.
- [ ] 사용자 소유 도메인·운영 인증 리디렉션·배포 환경을 확정한다. 계정 권한 승인이나 도메인 소유권 확인은 사용자가 해당 서비스에서 수행한다.
- [ ] 문서상의 출시 차단조건과 모바일·접근성·기능 검증을 통과한 뒤 실제 공개 배포를 별도로 승인받는다.

현재 로컬 구현·정책 테스트를 위해 사용자가 비밀키를 제공할 필요는 없다. 실제 연동 시 필요한 서비스 계정·인증·도메인·출시 정책을 단계별로 안내한다.

참고: 로컬 테스트의 쿼리·마이그레이션 실행과 DB 종료 API는 [PGlite 공식 API 문서](https://pglite.dev/docs/api)를 따른다.
