# DARK MIRROR 4인 팀 운영

작성일: 2026-10-29

이 문서는 사용자와 확정한 Phase 1 팀의 역할 및 협업 원칙을 기록한다. 역할 이름은 책임 구분이며, 모두 별도 모델을 지정해야 한다는 뜻은 아니다. 각 에이전트는 별도 지정이 없으면 부모 에이전트의 기본 모델과 추론 설정을 상속한다. 이 문서는 전역 에이전트 설정을 변경하지 않는다.

| 역할 | 주된 책임 | Phase 1 산출물·검수 범위 |
|---|---|---|
| 총괄 | 작업 분배, 공통 구조·통합, 입력·상태·연동 경계, 오류 수정, 최종 검증과 보고 | 앱 기반과 공통 계약을 확정하고 실행 가능한 전체 결과를 통합한다. 명령 실행 결과와 미구현 범위를 사실대로 보고한다. |
| 기획 (`planner`) | 문서 간 일관성, 단계 범위, 사용자 흐름, 완료 기준과 후속 의존성 관리 | `codex/PHASE1_DECISIONS.md`, `codex/TEAM.md`만 작성한다. 원본 기획이나 앱 코드는 임의로 수정하지 않는다. |
| UX·프런트엔드 (`ux_frontend`) | 한국어 모바일 화면, 디자인 토큰·공통 UI, 반응형과 접근성 | 총괄에게 배정받은 UI 파일을 구현한다. 익명 진입·선택 입력·미연결 안내·준비 중 상태가 사용자가 이해할 수 있도록 드러나게 한다. |
| 검수 (`reviewer`) | 코드 품질·기능·보안·접근성에 대한 독립 점검 | 구현자와 분리하여 실제 파일과 실행 증거를 검토하고, 문제의 위치·재현 조건·영향·수정 방향을 보고한다. 직접 코드 수정은 하지 않는다. |

## 기존 역할의 적용 범위

`planner`의 요구사항·정보 구조·우선순위·수용 조건 책임은 유지한다. DARK MIRROR에서는 비진단 표현, 사주·MBTI와 테스트 분리, 동의·철회 흐름, Phase별 범위 관리도 함께 점검한다.

`reviewer`의 기존 지침에 있는 연구실 사이트 페이지나 `requireAdmin()`·`requireSuperAdmin()` 같은 특정 프로젝트 전용 규칙을 이 앱의 보편적인 필수조건으로 적용하지 않는다. DARK MIRROR의 게스트 허용 경로, 실제 인증 경로, 서버 소유권 검사, RLS, 민감 데이터 보호를 기준으로 판단한다. 후속 단계 기능이 Phase 1에 없다는 이유만으로 구현 실패라고 보고하지 않되, 현재 UI가 완료된 기능처럼 오인시키는지는 확인한다.

## 파일 소유권과 협업

- 총괄은 각 구현 작업을 맡기기 전에 파일 또는 모듈 소유권을 명시한다. 공통 타입·상태 계약을 먼저 공유하고 서로 다른 파일에서 작업한다.
- 기획 담당의 쓰기 소유권은 이 문서와 `codex/PHASE1_DECISIONS.md` 두 파일로 제한한다. 총괄과 UX 담당의 구체적인 구현 파일 배정은 작업 지시에서 관리한다.
- 같은 파일을 동시에 수정하지 않는다. 공통 파일 변경이 필요하면 소유자에게 요청하고 조정한 뒤 작업한다.
- 다른 팀원의 변경을 되돌리지 않는다. 기존 사용자 기획·초안 파일을 보존하고, 필요한 보완은 근거와 함께 별도 문서 또는 합의된 변경으로 남긴다.
- 검수자는 읽기·진단을 담당하고 수정은 해당 구현 소유자가 수행한다. 총괄은 통합 이후 수정 결과를 다시 확인한다.
- 코드 작성, 의존성 설치, 테스트 실행, 테스트 통과는 구분하여 보고한다. 데모·준비 중·실제 연동 상태를 혼동하지 않는다.

## 작업 순서

1. 기획이 Phase 1 범위와 결정 사항을 정리하고 총괄이 공통 계약·소유권을 확정한다.
2. 총괄과 UX 담당이 배정된 영역을 구현하고 통합한다.
3. 검수자가 현재 단계에 필요한 기능·접근성·보안 조건을 독립 점검한다.
4. 구현 소유자가 문제를 수정하고 총괄이 실제 검증 결과·작동 범위·다음 작업을 정리한다.

필요한 스킬은 해당 작업 담당자가 지침을 읽고 적용한다. 프런트엔드 디자인과 Next.js·React 관련 스킬은 구현·검수 범위에 맞게 사용하며, 배포·실제 인증·LLM 연동을 Phase 1의 화면 구현과 혼동하지 않는다.
